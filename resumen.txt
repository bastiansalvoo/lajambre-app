Fecha de revisión: 25-04-2026

==================================================
1) VISTA GENERAL DEL PROYECTO
==================================================

El proyecto está dividido en dos aplicaciones principales:

1. Backend en NestJS + Prisma + PostgreSQL.
2. Frontend móvil/web en Expo Router + React Native + NativeWind.

Idea funcional del negocio:
- App de hamburguesería con catálogo de productos.
- Carrito de compra.
- Sistema de usuarios con autenticación JWT.
- Sistema de pedidos.
- Integración de pago con Webpay Plus (Transbank).
- Sistema de fidelización por puntos y recompensas.
- Vista/flujo administrativo para gestionar menú.

Estado macro actual:
- Backend: muy avanzado y con mucha lógica de negocio ya implementada.
- Frontend: base visual y navegación bastante avanzadas, pero varios flujos críticos aún en construcción (auth real, checkout real, historial y perfil, resultado de Webpay).

2.8 Pedidos y pagos (núcleo de negocio)

Esta parte está bastante robusta.

Pedido (create):
- Crea orden dentro de transacción.
- Valida usuario existente.
- Procesa productos y extras con validación de disponibilidad.
- Calcula subtotal + delivery + descuentos por recompensa.
- Controla reglas especiales (ej: premios que requieren hamburguesa).
- Descuenta puntos al momento de crear pedido si hubo canje.
- Registra transacción de puntos REDEEMED.

Pago (startPayment):
- Valida que orden esté PENDIENTE.
- Si total = 0 (pagado por canje), marca PAGADO y retorna flujo gratuito.
- Si total > 0, crea transacción Webpay, guarda buyOrder/sessionId y retorna token/url.

Confirmación (confirmPayment):
- Confirma token con Webpay.
- Si autorizado:
	- marca orden PAGADO,
	- calcula puntos ganados (con multiplicador martes),
	- suma puntos al usuario,
	- registra transacción EARNED con vencimiento a 90 días.
- Si rechazado:
	- marca orden CANCELADO,
	- devuelve puntos previamente canjeados,
	- registra transacción compensatoria.

Gestión de pedidos:
- Listado por usuario.
- Listado global admin.
- Obtener detalle por id validando ownership.
- Cambio de estado (admin).
- Cancelación manual con devolución de puntos.

Conclusión pedidos/pagos:
- Aquí está gran parte de la “inteligencia” del sistema y está implementada.

4) HALLAZGOS IMPORTANTES AL REVISAR TODO
==================================================

4.1 Backend está muy avanzado, pero hay inconsistencias puntuales

1. Inconsistencia de rewardType entre DTO y servicio de órdenes.
	 - DTO CreateOrderDto acepta: FREE_DELIVERY, FREE_BEVERAGE, FREE_BURGER.
	 - OrdersService espera: queso, bebida, papas, delivery, etc.
	 - Esto hoy puede romper validaciones al crear pedidos con recompensas.

2. Inconsistencia de campos address/phone en CreateOrderDto.
	 - DTO exige address y phone.
	 - En lógica actual de OrdersService esos campos no se guardan en Order (modelo no tiene esas columnas).
	 - Quedan “desacoplados” entre contrato API y persistencia real.

3. Seguridad temporal en upload de imagen.
	 - Guardias admin están comentados en PATCH /products/:id/image.
	 - Probablemente se dejó así para avanzar rápido en integración móvil.

4. URL de imagen en ProductsService.
	 - findAll transforma image a URL completa.
	 - findOne retorna valor sin transformación.
	 - Puede generar comportamiento distinto según endpoint consumido.

5. Tipo OrderWithDetails incluye address, pero el modelo Order no tiene ese campo.
	 - Ahora se disimula con casteos unknown.
	 - Conviene limpiar tipos para evitar errores ocultos.


4.2 Frontend está a mitad de camino funcional
